# DNSM - complete vulnerability list & PoCs

All six PoCs below were run against the current `dnsm.c` and confirmed
working. The easiest way to run them is all-in-Docker (nothing binds a host
port); you can also run a local build (`make && ./dnsm`) and point the scripts
at `127.0.0.1`.

Each script takes `host`/`port` from `argv` with localhost defaults, drives the
bug purely over the network, and prints `[+]` on confirmed success or `[-]` on
failure.

## Runtime secret (`DNSM_FLAG`)

The per-deployment secret comes from the `DNSM_FLAG` environment variable
(generated by the repo's `generate-secrets.sh`; empty/unset falls back to
`FLAG{local-dev-default}` for local dev). `entrypoint.sh` writes it to
`/home/ctf/dnsm/secret/flag.txt`, OUTSIDE `DNSM_ZONE_DIR`, so the
unauthenticated `/zone` path-traversal bug (#5) can read it. The files UNDER
`DNSM_ZONE_DIR` carry no secret (the flag is never written there), which is
exactly what lets `/zone` serve them to anyone without it being a disclosure
on its own.

The shared fleet metadata service (`../../metadata-service`, the SSRF target for
#4) also reads this deployment's `DNSM_FLAG` from its own environment (passed as
`META_SECRET_DNS`) and serves it at `/secret/dns`, so #4's disclosure is checked
against the same real per-deployment value, not a string checked into the repo.

## Run it all in Docker

The compose file brings up `dnsm`, the shared `metadata` service (the SSRF
target, on a `backend` network the attacker can't reach), and a `poc` runner. The
default `poc` command runs PoC #1 (the one-shot compression-pointer-loop
crash):

```
docker compose -f vuln_tests/docker-compose.yml run --build --rm poc
```

Run any other PoC by overriding the command (service name `dnsm`, port `8053`;
admin `8080`):

```
docker compose -f vuln_tests/docker-compose.yml run --rm poc python3 02_response_build_overflow.py dnsm 8053 8080
docker compose -f vuln_tests/docker-compose.yml run --rm poc python3 04_admin_ssrf.py            dnsm 8080 http://metadata:9000/secret/dns
docker compose -f vuln_tests/docker-compose.yml run --rm poc python3 05_zone_file_traversal.py   dnsm 8080
docker compose -f vuln_tests/docker-compose.yml run --rm poc python3 06_cname_chain_dos.py       dnsm 8053
docker compose -f vuln_tests/docker-compose.yml run --rm poc python3 08_admin_auth_bypass.py     dnsm 8080
```

#1 and #2 each crash the `dnsm` process (that's the point - see below), and
the container no longer runs a respawn supervisor, so the server stays down
after either fires. #6's PoC floods the resolver with self-referential CNAME
queries until the leaked permanently-spinning threads hit the container's
`pids_limit`, wedge the listener, and deny service to a *separate* ordinary
client (it confirms by that bystander denial, never by the attacking query's
own hang). Either way, restart the `dnsm` container before the next PoC that
needs a live server:
`docker compose -f vuln_tests/docker-compose.yml restart dnsm`.

> #6 must be run against a `dnsm` image built from the CURRENT source. A stale
> image that predates the unbounded-chain code caps the CNAME walk, answers
> loop queries instantly, and spins no threads - the PoC then correctly reports
> "not a full DoS" instead of false-passing. Pass `--build` (or rebuild dnsm)
> so the running image matches the source under test.

When you're done: `docker compose -f vuln_tests/docker-compose.yml down`.

## The list

| # | Vulnerability | Location | PoC |
|---|---|---|---|
| 1 | Name-decompression pointer loop -> one-shot process crash (no write bound + no loop guard: a `<label><ptr-to-itself>` QNAME overruns `qname[256]`) | `parse_name()` (via `parse_question()`) | `01_compression_pointer_loop.py` |
| 2 | Response-build stack buffer overflow (fixed TCP buffer, unchecked copy) | `tcp_worker()` + `append_rr()` (`assemble` `enforce=0`) | `02_response_build_overflow.py` |
| 4 | SSRF via admin "import from URL" (no scheme/host allow-list) discloses the runtime secret | `http_fetch()`, from `admin_worker()` | `04_admin_ssrf.py` |
| 5 | Path traversal via the **unauthenticated** `/zone` read endpoint (unsanitised `name=`) discloses the runtime secret | `admin_worker()` `/zone?name=` | `05_zone_file_traversal.py` |
| 6 | Unbounded CNAME-chain following -> mass thread/CPU exhaustion (no depth/loop limit, no cap on concurrent per-datagram threads) | `collect()` + `udp_server()` | `06_cname_chain_dos.py` |
| 8 | Fail-open admin auth: `X-Admin-Token` is "required" but only a *wrong* token is rejected; omitting it bypasses the gate to reach reload/import | `admin_worker()` auth gate | `08_admin_auth_bypass.py` |

## Notes on how these interact

- **#1 and #2 are the two halves of "hand-rolled C parsing of a length/pointer
  format."** #1 is a *parse-side* bug (expanding an inbound compressed name
  into a fixed buffer with no bounds/loop check); #2 is a *build-side* bug
  (serializing an outbound record into a fixed buffer with no size check).
  They share the "fixed stack buffer, attacker-influenced length" root cause
  but live on opposite ends of the message lifecycle, and fixing one does
  nothing for the other. Both PoCs crash the process: #1 overruns the inbound
  `qname[256]` by looping a compression pointer over a label with no write
  bound; #2 overruns the outbound response buffer with no size check.

- **#2 and #4 flow through the admin import feature; #5 does not.** #4 (SSRF) is
  an unsafe input path *into* `/admin/import`, and #2 uses that same feature as
  the delivery mechanism to plant the oversized TXT record it later queries over
  TCP. The admin side-channel is meant to be an internal-only ops convenience
  gated by a bearer token, but that gate is fail-open (#8): it blocks a *wrong*
  `X-Admin-Token` yet lets a caller who omits the header through. **So that
  fixing #8 cannot flip #2/#4 to "fixed", those two PoCs present a VALID
  `X-Admin-Token`** (the per-deployment `DNSM_ADMIN_TOKEN`, from the env;
  local-dev default `dev-admin-token`) - i.e. they are credentialed the normal
  way and test their own sink in isolation. A team that fixes only the gate (#8)
  still has an open SSRF (#4) and build-overflow delivery (#2) behind it, and
  both keep firing.

- **#5 is a standalone, UNAUTHENTICATED traversal, not an admin bug.** It lives
  on the public `/zone?name=` read endpoint (the HTTP sibling of AXFR - a
  read-only "zone transparency" feature), which takes no token at all. Its PoC
  sends no credentials; that is the point. Because the served zone files carry
  no secret (the flag is only written to the out-of-root `flag.txt`, never
  under `DNSM_ZONE_DIR`), the endpoint is safe to expose, and the *only* secret
  reachable through it is the out-of-root `flag.txt` via `../` traversal. #5 is
  therefore independent of both the admin gate (#8) and the admin import sinks
  (#2/#4): no admin escalation precedes it, and hardening `/admin/import` does
  nothing to it. (The `/admin/import?path=` import-from-file feature is
  separately confined to `DNSM_ZONE_DIR` via realpath + prefix-check, so it is
  *not* a second traversal sink.)

- **#8 is a front-door auth bug, scored on its own, NOT a gate the other PoCs
  lean on.** Because it's application-layer auth (a token in the request), not a
  network ACL, the scoring harness and the exploit run from the same place yet
  get different outcomes: a legitimate caller sends the token and its imports
  succeed, while #8's PoC specifically omits the token to prove the fail-open
  bypass. Fixing #8 (require the token to be present AND correct) shuts the
  front door for unauthenticated callers; it does nothing to the
  still-separately-broken input handling in #4, and #2/#4 - which now carry the
  token - keep proving those sinks regardless.

- **#4's severity depends on network position.** In the compose network the
  shared `metadata` SSRF target sits on a `backend` network the `poc` container
  is not attached to, so the *only* path to its secret is through `dnsm`, which
  bridges both networks. That's what turns "the admin fetched a URL" into a
  genuine trust-boundary crossing. The same target is meant to be shared across
  the fleet (see `../../metadata-service`): any module with an SSRF-class fetch
  can be pointed at it.

- **#1 and #6 are the same root cause - "follow a reference with no loop
  guard" - in two different places, but they surface very differently.** #1
  loops inside the *parser* following a compression pointer; #6 loops inside
  the *resolver* following zone CNAME records. The difference is what the loop
  touches: #1's loop *writes* each turn (it copies a label into `qname[256]`
  with no write bound), so it overruns the stack almost immediately and
  crashes the whole process off a single datagram; #6's loop does no unbounded
  write, so it just spins one CPU. **#1's PoC fires two probes so a HALF fix
  can't score as a whole one:** probe A is the self-referential pointer loop;
  if a loop/visited guard stops that, probe B sends a ~4 KB *uncompressed* name
  (no pointer at all) that overruns `qname[256]` purely on the missing write
  bound. A loop-guard-only fix passes A but crashes on B - so #1 is reported
  fixed only when parse_name both guards loops AND bounds every write. `udp_server()` hands each datagram to its
  own detached thread so one spinning #6 request can't wedge the listener for
  everyone else - real isolation that holds for *one* query but does nothing
  to stop an attacker sending many, which is why #6 is exercised as a
  mass-exhaustion flood. A depth/visited guard fixes the loop in both places;
  #1 *additionally* needs a write bound in `parse_name` (see fix #1).

- **#1 and #2 are both full-service crashes, and there is no respawn loop.**
  A stack overrun in any worker thread is a process-wide SIGSEGV, and
  `entrypoint.sh` runs `dnsm` in the foreground with no supervisor, so once
  either PoC fires the server stays dead until the container is restarted.
  Students should note that "just a crash" here is a full-service outage off a
  single packet, not a per-connection failure - restart `dnsm` before any
  later PoC that needs a live server.

## Fix directions (brief - save the detail for when they ask)

1. Bound every write in `parse_name` against the output buffer size, bound
   every read against the message length, and cap compression-pointer jumps
   (and require each pointer to move strictly backward) to kill the loop.
   Independently, cap `udp_server()`'s concurrent worker threads (a bounded
   pool/queue instead of an uncapped thread-per-datagram) so even a bug that
   *does* hang a handler can't be turned into mass exhaustion by volume alone.
2. Serialize responses into a correctly-sized buffer and length-check every
   append (`append_rr` must know its capacity), on the TCP path exactly as the
   UDP path already does; truncate + set TC instead of overflowing.
4. Allow-list the schemes/hosts the import feature may fetch (and block
   internal/link-local ranges); require authentication on the admin channel.
5. Confine the `/zone?name=` read to `DNSM_ZONE_DIR`: reject any `name`
   containing `..` or a leading `/`, then `realpath()` the resolved path and
   confirm it still begins with the canonical `DNSM_ZONE_DIR` *plus a trailing
   separator* (so a sibling like `zones-evil` can't satisfy a bare prefix
   match) before reading it. Note this is a containment fix, NOT "add a token" -
   the endpoint is meant to stay public; a legitimate `name=example.zone` must
   keep working. (The `/admin/import?path=` import-from-file feature already
   applies exactly this confinement.)
6. Cap CNAME-chain depth (e.g. ≤ 8) and track visited names to break loops
   during resolution. As with #1, also cap concurrent worker threads so volume
   alone can't turn one slow/looping class of query into a shared-service DoS.
8. Make the admin gate fail-closed: require `X-Admin-Token` to be *present* and
   equal (reject a missing/empty header, not just a wrong one), and compare in
   constant time. The one-liner is flipping the check from "reject only if a
   token was supplied and it mismatches" to "reject unless a token was supplied
   and it matches." Independently, still authenticate/allow-list the import
   sinks (#4/#5) - defence in depth, since a leaked token shouldn't hand an
   attacker SSRF/traversal.
